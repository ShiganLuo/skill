# GPU / X Server Freeze and Failure Troubleshooting

Diagnostic workflow for "the system seems hung / mouse won't move / black screen / can't log in" symptoms on Linux laptops, especially those with hybrid (integrated + discrete) GPUs running KDE Plasma on X11.

## Symptom vocabulary

Users describe the same underlying problem in many ways. Translate before diagnosing:

| User says | What actually happened |
|---|---|
| "笔记本死机，无法移动鼠标" | X server died or window manager crashed; X11 layer may still respond but nothing visible |
| "卡死，黑屏" | Xorg failed to start (e.g. `no screens found`); SDDM cannot render the greeter |
| "重启后又被踢回登录界面" | sddm-helper crashed when starting the user's session; check Xorg.0.log.old |
| "卸载 XX 之后还是卡" | The user's causal model is wrong; the real cause is unrelated (see Workflow §4) |

The key distinction: **kernel panic vs window-manager death vs display-server startup failure** produce visually similar "frozen" states but live in completely different layers.

## Diagnostic Workflow

Run steps in order. **Don't jump to fix proposals before completing step 4** (file provenance). The user explicitly corrects mid-diagnosis "asking which fix you want" without completing root cause.

### 1. Confirm the current session is healthy

If the user is talking to you right now, the system is at least responsive enough for the agent to run commands. Check whether the *current* session has any of the symptoms, or whether the user is describing a past event:

```bash
uptime
# If uptime is minutes, the user has just rebooted — they're describing what happened before
ps -o pid,etime,pcpu,pmem,comm -p $(pgrep -d, kwin_x11 plasmashell 2>/dev/null) 2>&1
# If kwin/plasmashell ETIME matches uptime, they're fresh and stable
```

### 2. Find the actual crash / freeze timestamps

Don't assume "the latest crash file" matches "the problem the user is reporting". Verify:

```bash
ls -lt /var/crash/ | head
# Note mtime on every *_usr_bin_*.crash file
stat -c "mtime: %y" /var/crash/_usr_bin_kwin_x11.*.crash /var/crash/_usr_bin_plasmashell.*.crash
# Pair crash file mtime with journalctl timestamps to reconstruct the actual sequence
```

### 3. Check display layer vs kernel

```bash
journalctl -k -p err --since "2 hours ago" --no-pager | tail -50
# Look for: amdgpu errors, nvidia module failures, ACPI errors
# If kernel log is quiet, the problem is NOT in the kernel

journalctl --since "2 hours ago" --no-pager | grep -E "kwin|XIO error|Fatal server error|graphics reset|context lost|GL .*reset"
# Look for: XCB errors (BadDamage 152), XIO fatal IO error, kwin_scene_opengl graphics reset
```

**Reading the error:**

- `kwin_scene_opengl: A graphics reset attributable to the current GL context occurred` — usually a downstream symptom, not root cause. The upstream is Xorg failing or the GPU driver entering a bad state.
- `XIO: fatal IO error 0 (Success) on X server ":0"` — X server died. Look for what killed it.
- `BadDamage (152) XCB error` — X server received a request for a destroyed DAMAGE object. Symptom of resource management churn, not a cause.
- `kwin_x11: The X11 connection broke` — kwin lost its connection. Either X died, or kwin died. Look at which happened first.

### 4. Audit Xorg configuration files — the most likely cause on hybrid GPU laptops

```bash
ls -la /etc/X11/xorg.conf.d/ /usr/share/X11/xorg.conf.d/
# List every .conf file with mtime

dpkg -S /etc/X11/xorg.conf.d/*.conf 2>&1
# Files with "no path found matching pattern" are USER-WRITTEN, not from any package
# These are the prime suspects for configuration conflicts

cat /etc/X11/xorg.conf.d/*.conf /usr/share/X11/xorg.conf.d/*.conf
# Look for: PrimaryGPU, AllowNVIDIAGpuScreens, multiple Driver sections for the same card,
# conflicting DRI versions, hand-written BusID values
```

**Common conflict pattern (the one this reference was written for):**

A hybrid GPU laptop with AMD iGPU connected to the internal display, plus an NVIDIA dGPU. Symptoms: intermittent SDDM crashes, kwin XIO errors, eventually users report "system hang". Root cause is usually one of:

1. **Multiple NVIDIA `Device` sections across files** — `/etc/X11/xorg.conf.d/10-hybrid-gpu.conf` (user-written) + `/usr/share/X11/xorg.conf.d/10-nvidia.conf` (package) + `/usr/share/X11/xorg.conf.d/11-nvidia-offload.conf` (regenerated by gpu-manager every boot) all define NVIDIA. Xorg merges them but the merged result can be inconsistent across boot sequences depending on file load order.
2. **`PrimaryGPU true` on the wrong card** — `Option "PrimaryGPU" "true"` in a hand-written config forces Xorg to treat NVIDIA as primary even though the physical display is on the AMD iGPU. Some boots succeed, some fail with `no screens found` depending on driver probe order.
3. **gpu-manager auto-generation conflicts with manual config** — `/usr/share/X11/xorg.conf.d/11-nvidia-offload.conf` is regenerated every boot by gpu-manager based on what it detects. If a manual config disagrees with gpu-manager's detection, behavior is undefined.

### 5. Check gpu-manager's view (the source of truth)

```bash
cat /var/log/gpu-manager.log
# Key fields to read:
#   "Vendor/Device Id: ... Is boot vga? yes/no"   → tells you which GPU the firmware chose as primary
#   "Found /dev/dri/cardN, driven by ..."         → tells you the actual DRI numbering
#   "Number of connected outputs for /dev/dri/cardN: N" → physical displays attached
```

If gpu-manager says AMD is `boot vga=yes` and has 1 output (the internal display), but the user-written Xorg config says NVIDIA is PrimaryGPU, that's the contradiction to investigate.

### 6. Cross-reference with bash_history

When a manual config exists but the user can't remember why, bash_history reveals when and in what sequence:

```bash
grep -niE "nvidia|prime|hybrid|gpu|xorg|sddm|prime-select|gpu-manager|blacklist|tee.*conf" ~/.bash_history
```

Pair this with `stat <file>` mtime to pin down when the user actually wrote each config.

### 7. Verify the DRI device enumeration

```bash
ls -la /dev/dri/
ls -la /dev/dri/by-path/
# card numbering reflects kernel probe order, not PCI BusID
# In normal hybrid: card0 = iGPU (or NVIDIA, depending on driver load order), card1 / card2 = the other
# Missing card0 while card1/card2 exist → driver loaded in unusual order → Xorg may fail
```

## Smoke Test After Fixing

Once you've cleaned up the conflicting configs, verify before declaring victory:

```bash
sudo reboot
# After login:
cat /var/log/Xorg.0.log | grep -E "Fatal|EE.*No devices|EE.*no screens"
# Expected: no output
xrandr --listproviders
# Expected: integrated GPU as Sink Output, dGPU as Source Output
journalctl -b --no-pager | grep -E "kwin.*XIO|graphics reset"
# Expected: no output
```

If any smoke-test check fails, the fix was incomplete — go back to step 4.

## Fix Recipes

### Remove conflicting manual Xorg configs

```bash
# Identify first
dpkg -S /etc/X11/xorg.conf.d/*.conf | grep "no path found"   # user-written only

# Then remove (after showing user the diff)
sudo rm /etc/X11/xorg.conf.d/<user-written>.conf
sudo reboot
```

### Confirm prime-select state

```bash
cat /etc/prime-discrete
# Should be: nvidia | on-demand | intel | unknown
# Most hybrid laptops should be "on-demand" if user wants battery life + occasional dGPU use
```

`prime-select` reads/writes:
- `/etc/prime-discrete` — the mode file
- `/lib/modprobe.d/nvidia-kms.conf` — KMS enable flag
- `/lib/modprobe.d/nvidia-runtimepm.conf` — runtime power management flag
- `/etc/modprobe.d/blacklist-nvidia.conf` — only present when in intel mode

### Don't manually set PrimaryGPU on hybrid laptops

If the physical display is wired to the iGPU (which gpu-manager's `boot vga` field tells you), do not set `PrimaryGPU true` on the dGPU. This is the single most common source of "system freeze on hybrid GPU laptop" problems. Use `prime-run <app>` or environment variables like `__NV_PRIME_RENDER=1` to direct specific apps to the dGPU.

### DRI version

`Option "DRI" "2"` is outdated. Modern Xorg defaults to DRI3. If you see `DRI "2"` in a hand-written config, that's a tell that the config was copied from an old tutorial.

## Pitfalls

- **Don't trust "GL reset" as the root cause.** `kwin_scene_opengl: A graphics reset` is a *symptom* — it tells you the GL context became invalid, not why. Always look upstream.
- **Don't attribute the freeze to whatever the user just uninstalled.** Users often uninstall the most recent thing they touched. Verify the actual crash time against the user's actions.
- **Don't `modprobe -r nvidia`.** Modern NVIDIA driver depends on modules that won't unload. Plan for reboot.
- **`sudo` is often not passwordless on user systems.** Don't assume you can run `sudo <anything>` — check the password prompt or the user's documented sudoers config first.
- **Crash files can be empty.** When kwin or plasmashell crashes, the `.crash` file may be 0 bytes if apport couldn't capture the core. Check journalctl for the actual signal/exit code.
- **gpu-manager regenerates files on every boot.** Editing `/usr/share/X11/xorg.conf.d/11-nvidia-offload.conf` directly is futile — it gets overwritten.

## What this reference does NOT cover

- Wayland-specific freezes (kwin_wayland, GNOME Mutter on Wayland) — different subsystem, different fix patterns
- Kernel-level GPU hangs (driver-internal fault, ring timeout) — those need `nvidia-bug-report.sh` and driver-side diagnostics
- Discrete-only desktops (no iGPU) — `PrimaryGPU` is fine there
- Optimus on Windows (different ecosystem entirely)
